# Text-to-SQL evaluation harness

Compares LLMs from Anthropic, OpenAI, and Google on 150 Spider dev questions by
**executing** their SQL against the real SQLite databases and checking the result, sliced
by Spider's difficulty labels, with paraphrase-pair consistency, cost, and confidence
intervals. Every design decision and the reasoning behind it is in [NOTES.md](NOTES.md).

## Setup

```bash
python3.13 -m venv .venv
```

```bash
.venv/bin/pip install -r requirements.txt
```

```bash
.venv/bin/python download_data.py
```

The last step fetches `validation.json` and the 20 dev databases (pinned revision); skip it
if `data/database/` is already populated.

## Check the harness before spending money

```bash
.venv/bin/python -m pytest -q
```

```bash
.venv/bin/python -m harness selfcheck
```

`selfcheck` runs the gold SQL (must score 100%) and an empty-result baseline (must score
0%) through the full pipeline. No API calls.

## Run models

Each vendor needs its own key, and only for the models you run. Put them in `.env`
(gitignored, loaded automatically; shell variables take precedence):

```bash
cp .env.example .env
```

Then fill in the keys and confirm which models are ready:

```bash
.venv/bin/python -m harness models
```


| vendor | env var | roster names |
|---|---|---|
| Anthropic | `ANTHROPIC_API_KEY` (or an `ant auth login` profile) | `opus-5`, `sonnet-5`, `haiku-4.5` |
| OpenAI | `OPENAI_API_KEY` | `gpt-5.6-sol`, `gpt-5.6-luna` |
| Google | `GEMINI_API_KEY` | `gemini-3.1-pro`, `gemini-3.8-flash` |
| Open-weight (local) | none; a running [Ollama](https://ollama.com) server | `qwen3-8b` |

Models are defined in [models.yaml](models.yaml), with one flagship-tier and one low-cost
model per vendor.

Open-weight models run through any OpenAI-compatible Chat Completions server (Ollama by
default; set `base_url` for vLLM, llama.cpp or LM Studio). For the roster model:

```bash
ollama pull qwen3:8b
```

```bash
ollama serve
```

The roster pins the weights' digest, and the run stops before the first request if the
local tag now points at different weights.

Smoke-test each model on 10 cases first. This checks the key, the model ID, and the
request format, and shows the real cost per case:

```bash
.venv/bin/python -m harness run gpt-5.6-luna --limit 10
```

Full runs (150 cases each; results go to `runs/<timestamp>_<model>/`):

```bash
.venv/bin/python -m harness run opus-5
```

Every model runs at high reasoning effort, so cost is driven mostly by output (thinking)
tokens, which is why the smoke run is worth doing first.

A run that stops partway (Ctrl-C, outage) resumes where it left off and retries the
failed cases:

```bash
.venv/bin/python -m harness run opus-5 --resume runs/<run_dir>
```

`--reps N` repeats each case N times to measure run-to-run variance.

## Read the results

```bash
.venv/bin/python -m harness compare runs/<opus_run> runs/<gpt_run> runs/<gemini_run> --out comparison.md
```

This prints accuracy per difficulty with 95% CIs, the paraphrase flip rate, and cost for
each run, then paired differences against the first run.

```bash
.venv/bin/python -m harness audit runs/<run_dir>
```

This writes `audit.md`, an adjudication sheet with gold vs predicted SQL and results for
every failure. When the grader turns out to be wrong about a case, add an `alt_gold_sql` to
it in `cases.yaml` (or fix the grader), then re-score without calling the model again:

```bash
.venv/bin/python -m harness regrade runs/<run_dir>
```

Other commands: `report RUN_DIR`, `prompt CASE_ID` (shows the exact prompt), `models`.

## Layout

| path | what |
|---|---|
| `cases.yaml` | the test set (generated by `build_testset.py`, then annotated by hand) |
| `models.yaml` | model roster |
| `harness/sqlexec.py` | sandboxed read-only SQL execution |
| `harness/grader.py` | execution-match grading rules |
| `harness/prompt.py` | prompt (versioned) |
| `harness/models.py` | Anthropic, OpenAI, Gemini providers + oracle / null baselines |
| `harness/runner.py` | runs, resume, regrade |
| `harness/report.py` | metrics, clustered bootstrap CIs, comparisons |
| `harness/audit.py` | adjudication sheet |
| `analysis/grader_mutations.py` | measures how many wrong queries the grader lets through |
| `runs/<id>/` | `manifest.json`, `results.jsonl`, `errors.jsonl`, `report.md`, `summary.json`, `audit.md` |

## Included results

`comparison.md` and `runs/` hold the results of the cross-vendor comparison. Each manifest's
`git.commit` (`d06cd8b`) is in this repository's history; `dirty: true` means the working tree
had uncommitted changes at run time. OpenAI organization IDs in logged error messages are
replaced with `org-REDACTED`.
